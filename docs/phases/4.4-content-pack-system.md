# Fase 4.4 — Content Pack System

## 1. Estado

**CERRADA.**

La rama histórica `feat/content-pack-system` se creó sobre el cierre de 4.3 y
se integró posteriormente en `main`. La integración fue lineal: `main` avanzó
de `4bb7d90` a `c2af608` sin crear un merge commit. La rama conserva valor
histórico, pero no es necesaria para utilizar ni continuar el proyecto.

La fase no añadió código de producción. Su resultado fue reconciliar el nombre
reservado en el roadmap con la infraestructura que 4.2 ya había construido,
documentar sus fronteras y cerrar el alcance sin introducir abstracciones
especulativas.

## 2. Objetivo original

El roadmap había reservado 4.4 para el **Content Pack system**. Antes de
implementar nada se auditó el repositorio para responder una pregunta concreta:

> ¿Qué falta realmente para que CoreRPG disponga de un sistema de Content Packs
> útil para continuar?

La auditoría debía distinguir una carencia real de una etiqueta histórica del
roadmap. No se asumió que una fase con nombre propio necesitase automáticamente
nuevos tipos, APIs o formatos.

## 3. Descubrimiento principal

La fase 4.2 ya había construido sustancialmente la infraestructura genérica del
Content Pack system. El modelo lógico incluía:

- `PackId` y `DefinitionId` como identidades fuertes;
- `ResourceKind` como clase lógica canónica;
- `SemanticVersion` y `VersionRequirement`;
- `ContentManifest` y `PackDependency`;
- `ResourceDefinition` y `DefinitionReference`;
- `ContentDefinitionInput` y `ContentPackInput`;
- `ContentCatalog` y `ContentCompatibility`;
- diagnósticos estructurados y deterministas;
- validación global, atómica y todo-o-nada;
- dependencias de packs y referencias cross-pack directas.

La adaptación física opcional incluía además:

- Content Contract JSON `0.1.0`;
- schemas JSON Schema Draft 2020-12;
- lector JSON estricto;
- registro local y cerrado de schemas;
- mapping a tipos fuertes del Core;
- loader físico de un pack;
- loader multi-pack desde raíces explícitas;
- límites de lectura y protección frente a traversal y escapes de filesystem;
- aislamiento de jsoncons, JSON y filesystem en `CoreRPGContentJson`.

El orden de entrada no concede prioridad, los catálogos se publican sólo tras
validación completa y los diagnósticos se ordenan canónicamente. Implementar un
segundo “Content Pack system” habría duplicado responsabilidades ya cerradas.

## 4. Decisión de la fase

4.4 se convirtió en una fase de **redefinición y cierre de alcance**.

No se añadió código de producción porque la auditoría no encontró un requisito
inmediato que exigiese nuevas APIs, tipos, schemas o loaders. La ausencia de
código no fue trabajo omitido: fue la consecuencia de comprobar primero el
estado real y evitar una segunda arquitectura paralela.

El principio aplicado fue:

> No crear abstracciones sólo para llenar una fase del roadmap.

Cuando una necesidad futura disponga de consumidor, invariantes y casos de uso
concretos, podrá justificar una ampliación. 4.4 no intentó anticiparla.

## 5. `ResourceDefinition` actual

El contrato real al cierre es:

```text
ResourceDefinition = DefinitionId + ResourceKind
```

Ambos valores son poseídos por la definición. No contiene:

- payload;
- property bag;
- DOM JSON;
- objetos de dominio RPG;
- relaciones resueltas;
- schema runtime de dominio.

Esta simplicidad es intencional. El envelope identifica y clasifica una
definición sin decidir todavía cómo se representa contenido de dominio.

## 6. `ResourceKind`

`ResourceKind` es un identificador canónico abierto de clase lógica. Su
gramática es `[a-z][a-z0-9_-]*` y su valor no se deduce de `DefinitionId`.

No está acoplado a:

- una extensión de archivo;
- una ruta;
- un schema físico;
- un enum global de tipos RPG;
- un registry central oculto.

Permite declarar la clase de una definición y validar el tipo esperado de una
referencia. No se convirtió en una taxonomía cerrada porque todavía no existe
un conjunto real de tipos de dominio que justifique cerrarla.

## 7. `ContentCatalog`

`ContentCatalog` es un catálogo inmutable de definiciones que han superado la
validación global. Su API permite:

- comprobar existencia mediante `DefinitionId`;
- buscar una definición mediante `DefinitionId`;
- consultar su `ResourceKind`;
- enumerar definiciones en orden canónico.

El catálogo no ofrece todavía:

- payloads de dominio;
- modelos tipados como región o personaje;
- instancias vivas;
- spawning.

Los manifests, referencias de staging y localizadores físicos participan en la
construcción, pero el catálogo publicado conserva sólo las
`ResourceDefinition` ordenadas.

## 8. Referencias

El contrato real es:

```text
DefinitionReference = target DefinitionId + expected_kind
```

Durante la construcción del catálogo se valida:

- que el target exista;
- que su `ResourceKind` coincida con `expected_kind`;
- que una referencia cross-pack esté respaldada por una dependencia directa;
- que el conjunto completo siga siendo válido con independencia del orden.

No se almacenan punteros runtime directos entre definiciones ni se materializa
obligatoriamente un grafo resuelto. La resolución por identidad evita acoplar a
los consumidores con el almacenamiento interno y mantiene abiertas futuras
necesidades de reload o metadatos de relación.

## 9. Separación lógica y física

`CoreRPG` trabaja con el modelo lógico. `ContentPackInput` y `ContentCatalog`
no dependen de JSON, jsoncons o filesystem.

`CoreRPGContentJson` es la adaptación física opcional. Se ocupa de bytes JSON,
schemas, mapping, paths, lectura y carga de packs. Depende hacia `CoreRPG`; el
Core no depende de ella.

Por tanto, JSON, filesystem y schemas físicos no forman parte del dominio
principal. El principio para futuras extensiones es:

1. diseñar primero el modelo lógico;
2. decidir después cómo se representa físicamente.

El formato de transporte no debe dictar las invariantes del dominio.

## 10. Por qué no se añadieron payloads

La auditoría reconoció que el contenido útil necesitará en el futuro más
información que identidad y kind. Sin embargo, todavía no existían un primer
modelo real y un consumidor capaces de demostrar qué forma debía tener esa
información.

Por ello 4.4 no introdujo:

- `data: {}` ni property bags recursivas;
- `std::any`;
- blobs opacos;
- un DOM JSON dentro de Core;
- un `variant` global de todos los tipos RPG;
- jerarquías virtuales de payloads;
- registries globales de kinds o codecs.

Una representación genérica prematura habría condicionado ownership, tipado,
validación, serialización, interoperabilidad y evolución antes de conocer los
datos reales. Estas alternativas no se prohíben para siempre; sólo se reabrirán
ante requisitos y consumidores concretos.

## 11. Lore como fuente de requisitos

El proyecto dispone del repositorio separado
`robdor80/Videojuego_Nimroel`, dedicado a lore y worldbuilding. En fases
futuras podrá utilizarse una muestra representativa de ese material para
descubrir requisitos reales, por ejemplo qué información y relaciones necesita
una región, un asentamiento, una entidad política, una cultura, una especie o
un personaje.

El lore no se copia al Core. Nimroel se utiliza como fuente de casos reales, no
como hardcoding de la arquitectura. CoreRPG continúa siendo
universe-agnostic y sus fixtures permanecen neutrales.

## 12. Tres capas conceptuales

4.4 fijó una distinción entre:

1. **Motor genérico CoreRPG:** identidad, catálogo, compatibilidad, validación,
   estado vivo y reglas autoritativas.
2. **Posible dominio RPG reutilizable:** tipos concretos sólo cuando exista
   evidencia de invariantes compartidas por varios juegos.
3. **Universo Nimroel:** canon y contenido propios expresados por su Content
   Pack y sus integraciones.

La fase no decidió si `Region`, `Settlement`, `Culture`, `Species`,
`Character`, `Faction` o `PoliticalEntity` deben pertenecer a una capa RPG
reutilizable o permanecer en contenido específico. Esa decisión necesita
requisitos suficientes.

## 13. Definición de contenido frente a mundo vivo

La separación permanece explícita:

- `ContentCatalog` representa definiciones declarativas validadas e inmutables;
- `WorldState` representa la realidad viva de una partida.

4.4 termina en el lado declarativo. No implementa el puente general
`DefinitionId` -> `EntityId`, ni convierte automáticamente una definición en
una entidad viva.

## 14. Frontera con 4.5

La frontera de fases queda fijada así:

- **4.4:** definición y validación declarativa de contenido;
- **4.5:** evolución de `WorldState` hacia un Generic World State real.

Permanecen fuera de 4.4:

- registros vivos;
- lifecycle y eliminación;
- spawning;
- templates y archetypes;
- provenance de instancia;
- bootstrap del mundo;
- asociación viva `DefinitionId` -> `EntityId`.

4.5 puede comenzar sin reparar 4.4: dispone ya de identidad declarativa y viva
separadas, un catálogo validado y una frontera explícita entre posibilidades y
estado.

## 15. Content Contract JSON `0.1.0` intacto

4.4 no modificó:

- `docs/content-json-contract-0.1.0.md`;
- `schemas/content/0.1.0/`;
- `content_contract_version`.

No apareció implícitamente un contrato `0.2.0`. Cualquier extensión estructural
futura deberá diseñarse, validarse y versionarse explícitamente junto con su
contrato real.

## 16. Versiones intactas

El repositorio confirma al cierre:

- CoreRPG: `0.1.0`;
- Content Contract soportado: `0.1.0`;
- schemas: `0.1.0`;
- `example.test` y `example.addon`: pack version `1.0.0`.

Estos ejes siguen siendo independientes. 4.4 no cambió versiones para reflejar
una decisión exclusivamente documental.

## 17. Discovery y modding

Continuaron deliberadamente fuera de alcance:

- discovery automático de packs;
- registry global de packs instalados;
- traducción implícita de `PackId` a filesystem;
- auto-load de dependencias;
- search paths;
- ZIP y HTTP;
- hot reload;
- overrides y prioridades;
- patch packs;
- merge y last-wins;
- scripting;
- plugins ejecutables.

El caller continúa seleccionando y proporcionando raíces explícitas. Una
`PackDependency` expresa una relación lógica; no descubre una ubicación física.

## 18. Universalidad del Core

Al cierre de 4.4 el target principal `CoreRPG` sigue sin depender de:

- Nimroel o Norgar;
- Unreal Engine;
- OpenAI u otro proveedor externo;
- red;
- JSON o jsoncons en su dominio;
- filesystem en su dominio;
- gameplay específico.

La referencia documental al lore separado no introduce acoplamiento de
producción. La adaptación JSON continúa aislada en `CoreRPGContentJson`.

## 19. Scope creep evitado

Habría sido scope creep:

- inventar `Region` sin requisitos reales;
- crear una clase base `Character`;
- introducir un ECS;
- añadir un payload genérico “por si acaso”;
- crear un schema `0.2.0` sin consumidor;
- implementar discovery o un sistema de mods;
- añadir codecs o registries anticipadamente;
- implementar `DefinitionId` -> `EntityId` en esta fase.

Evitar estas decisiones fue parte del resultado de 4.4. Permitió conservar las
fronteras demostradas sin cerrar prematuramente las alternativas futuras.

## 20. Cambios reales de la fase

El único commit propio de 4.4 fue:

```text
c2af608 docs: redefine content pack system phase
```

El diff real respecto de `4bb7d90` afectó únicamente:

- `README.md`;
- `docs/architecture.md`.

Git registra 105 inserciones y 12 eliminaciones. No hubo cambios en producción,
tests, API, CMake, CI, schemas, fixtures, versiones ni contratos.

## 21. Tests y CI

4.4 no cambió comportamiento de producción ni añadió tests funcionales. No era
necesario crear casos que fingieran validar un sistema inexistente; la
validación relevante consistió en revisar el diff, comprobar su coherencia con
4.2 y confirmar que el repositorio permanecía limpio y las suites existentes no
regresaban.

El cierre operativo comunicó CI verde, después de integrar `c2af608` en `main`,
en:

- Windows / MSVC;
- Linux / GCC.

El entorno usado para redactar esta acta confirma commits, referencias locales
y estado integrado, pero no pudo consultar los metadatos remotos de las
ejecuciones: GitHub respondió `404` tanto por CLI como por acceso web. Por ello
no se inventan IDs, URLs ni logs de runs y la CI se registra explícitamente
como evidencia comunicada del cierre.

Las cifras históricas de tests de 4.2 y 4.3 permanecen en sus actas; 4.4 no las
recalcula ni las altera.

## 22. Criterios de cierre

La auditoría final comprobó:

- rama histórica publicada;
- working tree limpio antes de crear esta acta;
- commit `c2af608` presente e integrado en `main`;
- `main` sincronizada con `origin/main`;
- diff propio exclusivamente documental;
- coherencia con el sistema construido en 4.2;
- Content Contract JSON `0.1.0` intacto;
- schemas y versiones intactos;
- frontera 4.4/4.5 clara;
- ausencia de una necesidad demostrada de código adicional;
- CI verde comunicada para Windows/MSVC y Linux/GCC.

No se registraron blockers para el cierre.

## 23. Resultado arquitectónico

4.4 no construyó una segunda capa de Content Pack. Estableció que la
infraestructura de 4.2 ya era suficiente para continuar y fijó dónde detenerse
antes de introducir dominio, payloads o extensibilidad especulativa.

El resultado es una base con identidades, validación, dependencias, referencias
y carga física claramente separadas, pero sin pretender que el envelope actual
sea ya un modelo RPG completo.

## 24. Decisiones que requieren revisión explícita antes de cambiar

Al cierre son decisiones arquitectónicas vigentes:

- `ResourceDefinition` no adquiere automáticamente un payload arbitrario;
- JSON y filesystem no entran en el dominio de `CoreRPG`;
- `ResourceKind` sigue siendo abierto;
- `ContentCatalog` no es `WorldState`;
- `PackDependency` no descubre filesystem;
- las raíces explícitas continúan siendo explícitas;
- no existen override, prioridad o last-wins implícitos;
- no se introducen tipos de Nimroel en el Core genérico;
- todavía no existe el puente general `DefinitionId` -> `EntityId`;
- las extensiones futuras deben partir de requisitos reales.

No se declaran dogmas eternos. Cambiar estas decisiones exige una necesidad
concreta, revisión arquitectónica y actualización coherente de contratos y
tests.

## 25. Trabajo futuro intencional

Permanecen para fases posteriores:

- 4.5 — Generic World State;
- contenido tipado cuando exista modelo y consumidor;
- revisión de lore representativo antes de diseñar modelos concretos;
- evolución del contrato JSON cuando exista una extensión estructural real;
- discovery o modding sólo si sus casos de uso lo requieren.

No se reservó durante 4.4 un nuevo número de fase para contenido de dominio. Su
ubicación en el roadmap se decidirá cuando existan requisitos suficientes.

## 27. Lección de ingeniería

Un roadmap es una guía de evolución, no una obligación de generar código. Si
una fase anterior ya satisface sustancialmente los requisitos y no han aparecido
nuevos casos de uso, añadir abstracciones para conservar el nombre original de
la fase aumenta el coste sin aportar un contrato demostrado.

En 4.4 la decisión correcta fue auditar, reinterpretar y documentar. Posponer
una abstracción hasta disponer de evidencia conserva más opciones que publicar
una API prematura.

## 28. Cierre

La infraestructura genérica de Content Packs construida en 4.2 queda reconocida
como suficiente para continuar. 4.4 cierra sus fronteras sin duplicarla y sin
introducir contenido de dominio especulativo.

**FASE 4.4 CERRADA.**

CoreRPG queda preparado para comenzar **Fase 4.5 — Generic World State**.
