retiene ResourceDefinition (ID/kind): referencias se validan en staging y no
aportan semántica runtime. Ninguna carga crea edificios/NPC.

El modelo V1 se etiqueta todavía «en desarrollo»; V001 cierra el **alcance del
ensayo**, no pesos/layout/hogares. El handoff JSON declara que no es Content Pack.
Se extrae de él una proyección específica versionada, validada y trazable;
no se entrega ese handoff al decoder de CoreRPG. Las reglas ricas no caben en
0.1.0; usar un sidecar Nimroel satisface la frontera de payload sin 0.2.0,
property bag ni cambios al Core. El estado de roadmap/acta 4.12 estaba obsoleto:
GitHub confirma integración; sólo se actualizará el estado vivo del roadmap.

Revisión ligera Star Trek: README, AUDITORIA_F00, MATRIZ_REUTILIZACION y frontera
de ship_computer distinguen contratos offline de runtime y autoridad de Core.
Identidad, streams, relaciones sin semántica, lectura desde memoria y rechazo de
contenido incompatible sirven también a una dotación/nave. No se cambia su
contrato ni se duplica su capa de contenido; no se inicia UE5.

## I4 — Instancia estructural reproducible

`tests/nimroel_content_pack_test.cpp` consume el pack externo real; no usa mocks.
Carga desde bytes con read_json_document/decoders y compara con loader filesystem.
CatalogBuildResult rechaza corrupción/tipos/duplicados sin catálogo parcial.
Su target sólo existe al configurar CORERPG_NIMROEL_SOURCE_DIR y ContentJson ON;
CoreRPG y CoreRPGContentJson no incorporan código particular de Nimroel.

Receta `v001-structural-1`, generador `structural-fixture-1`, reglas
`v001-handoff-0.1`, fuente explícita de semilla 413001. Identidad estable
`region-fixture-1/node-0001`, independiente de nombres visibles (no generados).
Contexto `interior-timber-route-fixture` versión 1: dos nodos y una conexión rural
funcional para carros. No hay costes calculados, cobertura regional ni reglas
estacionales/hidrológicas resueltas. El stream 413 sólo prueba continuidad RNG.
No se ha implementado derivación regional de seeds ni generación procedural completa.

Cinco entidades iniciales: aldea, herrería/taberna como **nodos de servicio**, frontera
exterior abstracta y objeto de categoría agrícola. Reserva 50, materialización
acotada de dos identidades anónimas (observadores), 48 unidades latentes.
No hay profesión, biografía, nombre o edificio concreto atribuido a esos nodos.
Binding no aplica propiedades. RelationKind 1/2/3 son etiquetas estables de este
fixture para servicio/conexión/asociación poblacional, sin permisos o semántica
interpretada por el Core. Contener el objeto en un nodo no constituye custodia,
propiedad ni reparación. Las capacidades de agua/hogares/agricultura/etc. se
validan como requisitos declarativos; aún no se construyen sus instancias ricas.

ActionEngine y Simulation ejecutan un traslado estructural real. Rechazos de
binding, ciclo, reserva distinta, exceso de lote/latencia y límite de simulación
conservan snapshot y RNG completos. Mismas entradas y orden invertido de carga
producen catálogo, snapshot y bytes iguales. El bootstrap es inicialización de
un mundo nuevo; no es una transacción universal de creación de escenarios.

## I5 — Conocimiento y continuidad

Observador A conoce aldea/herrería/herramienta y hechos concretos; B conoce
aldea/taberna. Existencia en WorldState no da visibilidad. Se contrastan dato
no disponible y ausencia recordada. Un traslado/individualización posterior no
refresca contención/población recordadas. Grants explícitos conceden actualidad
sólo en la vista; retirarlos recupera el recuerdo y no crea Knowledge persistente.

El endpoint de prueba recibe únicamente ObserverView y filtros/límites; no es
invocable con catálogo o Inspector. ContextBuilder conserva orden FactKey,
filtros AND, presupuestos de examen/selección/contenido/capacidad, y resultado
uniforme para oculto/inválido/ausente. Consultar Inspector privilegiado no altera
vistas ni concede secretos. La frontera no aísla C++ hostil en el mismo proceso.

Snapshot v3 real guarda todas las tablas, memorias, revisión y streams. Round-trip
bytes/snapshot y load conservan binding/contención/relaciones/reserva/orígenes,
observadores separados, recuerdos antiguos y siguiente ID. El siguiente número
RNG y siguiente individualización coinciden. Grants no se serializan. Catálogo
ausente/incompleto, bytes corruptos y contenido incompatible se rechazan sin
publicar un mundo incompleto. Los formatos v1/v2 y sus fixtures históricos siguen
sin cambios; las regresiones anteriores se ejecutan completas.

Política exacta y ejemplo neutral fuera de la biblioteca:
[compatibilidad externa](../external-content-compatibility.md). Pack version,
conjunto ID/kind, huella y contexto inicial se comparan antes de load. No existe
migración automática de partidas entre versiones de canon ni I/O físico nuevo.

## Reproducción offline de las pruebas cruzadas

Con ambos checkouts ya disponibles, fijar Nimroel al SHA registrado arriba antes
de configurar. No se requiere red para esos datos; GoogleTest/jsoncons pueden
reutilizarse con FETCHCONTENT_SOURCE_DIR_GOOGLETEST/JSONCONS de revisiones fijadas
por el CMake existente. La biblioteca productiva no obtiene contenido remoto.

```sh
python -m pip install -r ../Videojuego_Nimroel/Tools/CoreRPG413/requirements.txt
cmake --preset dev -DCORERPG_NIMROEL_SOURCE_DIR=../Videojuego_Nimroel
cmake --build --preset dev --parallel 2
ctest --preset dev
cmake -S . -B build/core-only -DBUILD_TESTING=ON -DCORERPG_BUILD_CONTENT_JSON=OFF -DCMAKE_BUILD_TYPE=Release
cmake --build build/core-only --config Release --parallel 2
ctest --test-dir build/core-only -C Release --output-on-failure
cmake -S . -B build/sanitizers -DBUILD_TESTING=ON -DCORERPG_BUILD_CONTENT_JSON=ON \
  -DCORERPG_NIMROEL_SOURCE_DIR=../Videojuego_Nimroel -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_FLAGS="-fsanitize=address,undefined -fno-omit-frame-pointer" \
  -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=address,undefined"
cmake --build build/sanitizers --parallel 2
ctest --test-dir build/sanitizers --output-on-failure
```

El comando con --preset debe citar el argumento -D completo en PowerShell si
el valor comienza por punto; la CI ya lo hace. Las configuraciones sin paquete
externo conservan 435 tests con JSON y 326 sin JSON. Con el paquete son 447.
No se requiere red para jugar o cargar un pack instalado; los clones y descargas
de herramientas/dependencias son preparación de desarrollo/CI.

Evidencia local generada en el workspace de ejecución: logs y JUnit
`/workspace/scratch/413-{dev,core,san}.log` / `.xml`, y logs de build/configuración
con los mismos prefijos. No son dependencia de consumo ni se promete persistencia
externa de esos archivos; la CI ofrece registros por SHA en las PR. La suite
sanitaria local incluye todos los tests de ContentJson, no sólo los once nuevos.
