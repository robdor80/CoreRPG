## I3 — Diagnóstico compartido

`Inspector::diagnose` aplica a tablas prestadas el mismo validador estructural
que `Persistence::validate`; `diagnose_snapshot` explica un candidato sin cargarlo.
No se captura/serializa el mundo vivo. Se mantiene precedencia de errores y
codec v1/v2/v3. El primer fallo acota la salida a un valor fijo. Los códigos de
Persistence son identificadores técnicos estables; no se generan mensajes con
secretos para superficies jugables. Validez es `status == valid`; warning por
recursos significa comprobación inconclusa, nunca mundo válido.

Presupuestos por defecto: un millón de registros dispersos totales, 8 MiB de
payload scratch (8 bytes por población + 1 por vínculo). El allocator puede
necesitar overhead adicional; bad_alloc/length_error se traducen a resultado
inconcluso sin mutar. Identidades implícitas no reservan scratch. Coste:
O(L log L + M log P + K log K + D + R + S), más longitud de textos, para vínculos,
miembros, poblaciones, conocimiento, bindings, relaciones y streams de candidato.
No se intenta verificar memoria arbitrariamente corrupta ni disponibilidad de
un catálogo; restore continúa resolviendo bindings con catálogo explícito.

## I4 — Acciones y simulación

Se reutiliza `ActionResult` sin wrapper ni cambio de semántica: ya contiene
resultado/rechazo, revisiones, precondición y consecuencia tipada. Inspector
consulta el estado actual al retorno de process/step; no reconstruye el pasado,
no certifica procedencia de un ActionResult y no lo interpreta como permiso.
El Host suministra y conserva explícitamente resultados técnicos. No hay API
de historial ni registro automático. Sólo se leen resultados del prefijo
`processed` definitivo; inspeccionar no reejecuta acciones ni tiradas.

Ejemplo mínimo, exclusivamente dentro del Host de confianza:

```cpp
#include <corerpg/inspector.hpp>
#include <corerpg/simulation.hpp>
#include <array>

corerpg::WorldState world;
corerpg::RandomStreams random{42};
const auto unit = world.create_entity();
const auto destination = world.create_entity();
const corerpg::ActionRequest request{
    unit, corerpg::PlaceEntityAction{unit, destination}};
const auto result = corerpg::ActionEngine::process(world, random, request);
const corerpg::Inspector inspector{world};
const auto entity = inspector.entity(unit);
const auto diagnostic = inspector.diagnose();
const auto revision = inspector.metadata().revision;
const auto page = inspector.relations({0, 64, revision});
// Leer entity/page/result sólo en herramientas técnicas autorizadas.
// Descartar todos los préstamos ANTES de mutar o restaurar el mundo.
// La UI/NPC/IA recibe únicamente Visibility::project con permisos del Host.
```

La revisión de un resultado antiguo puede coincidir con una sesión restaurada;
el Host mantiene esa asociación, nunca se deduce de la igualdad numérica.
La regresión compara ejecución por Simulation con ejecución de las mismas
acciones intercalada con todas las consultas Inspector, incluyendo RNG, rechazos,
no-ops, resultados completos, snapshots y bytes. Recuerdos obsoletos permanecen
idénticos y válidos; entidades/relaciones/definiciones ocultas siguen fuera de
ObserverView aunque se hayan consultado técnicamente.

## Uso y clasificación de diagnósticos

| Estado | Significado técnico |
| --- | --- |
| `not_run` | Valor por defecto; ninguna comprobación realizada, no válido |
| `valid` | Invariantes comprobadas; código `success` |
| `invariant_violation` | Primer error de la validación compartida; código Persistence concreto |
| `limit_exceeded` | Presupuesto de registros/scratch o límites Persistence; inconcluso |
| `allocation_failure` / `capacity_failure` | Asignación/capacidad insuficiente; inconcluso |

`invalid_world` cubre contabilidad de identidades/revisión; `invalid_link`,
`noncanonical_links` y `cycle_detected` la contención. Familias `invalid_*` y
`noncanonical_*` identifican bindings, relaciones, poblaciones, miembros,
streams de candidato y conocimiento. Se comprueba orden/unicidad antes de buscar
referencias. Ningún código repara o refresca. Un resultado válido no acredita
permisos de gameplay, reglas de contenido de un universo o un catálogo cargado.
El preflight de presupuesto Inspector precede al validador; la precedencia
histórica dentro de Persistence se conserva.

Las páginas tienen orden canónico (IDs ascendentes; vínculos por entidad;
relaciones por source/kind/target; reservas por grupo; miembros por individuo;
recuerdos por sujeto/tipo/extremos dentro de observador). Cambiar filtro reinicia
offset. `next_offset` vacío indica final. Se itera `entities.first.value() + i`
para `i < count`; no se calcula un final exclusivo que pueda desbordar uint64.
Ante revisión obsoleta se descartan páginas y se reinicia sólo desde el Host.
Sin revisión esperada cada consulta observa el estado vigente de su llamada.

## Compatibilidad y límites pendientes

Se añade únicamente `include/corerpg/inspector.hpp` como interfaz pública y un
friend privado en WorldState para leer tablas sin clonarlas. Ninguna firma
pública anterior cambia; tampoco layout de WorldState, formato/versión/bytes de
snapshot, políticas RNG, ActionResult o Simulation. `Persistence::validate`
conserva sus checks de formato/recursos y delega la parte estructural al helper
compartido. No se cambia CI ni se quitan/relajan tests. Sin nuevas dependencias.

La biblioteca no impide que código Host de confianza entregue deliberadamente
información privilegiada: su responsabilidad es aislar herramientas técnicas de
UI/NPC/IA. No existe aislamiento de código hostil en el proceso. Se requiere
sincronización externa; no se prueban carreras prohibidas por el contrato.
Los informes prueban estructura, no reglas de gameplay ni integridad física de
memoria. `capacity_failure` maneja defensivamente length_error; no se fuerza un
vector del tamaño máximo en las pruebas.

Quedan para trabajo posterior, con su propia autorización: Context Builder/AI
4.12 (sin iniciarlo), historial/replay si se justifica, ABI/puentes nativos de
Nimroel y Trek, compilación/enlace/ejecución Android NDK ARM64 y prueba física
en Tab S9+. El consumidor conserva autenticación/autorización, sensores,
resolución de contactos y registros operativos. Inspector no certifica ninguno
de esos hitos. No se han modificado los repositorios consumidores.
